## 3. 公開停止の判断

判定：継続 / 一部停止 / メンテナンス表示 / 配信停止

判断日時・理由・責任者：

悪意あるスクリプト、偽サイトへの誘導、個人情報・認証情報の公開が疑われる場合は、影響を止める方法を決めます。アカウントが安全と確認できればメンテナンススイッチも使えます。アカウント・公開ワークフローの侵害が疑われる場合は、信頼できる管理経路から公開・編集経路を制限します。

メンテナンス表示だけではJSON、Git履歴、配信済みキャッシュは非公開になりません。情報の種類・影響に合わせて対応します。

## 4. ログと証跡の保全

- 改変前後のファイル、Gitコミット・差分、Actions記録、公開日時、画面、HTTP応答を保存する。
- 所有者が閲覧できるGitHubのセキュリティ履歴、CMSの保存・エラー記録、実際に使用する配信基盤のログを保存する。
- タイムゾーン、取得日時・取得者、ファイル名・ハッシュを記録する。
- 調査前に履歴・ログを消さない。共有資料から秘密値・個人情報を除く。

## 6. 正常版への復旧

復旧先コミット・成果物：

1. 正常と判断した根拠を保存し、別フォルダでチェックアウトする。
2. 不審な変更を除いた差分を作り、CMSで増えた正当な記事・写真を保持する。
3. 固定した依存でビルドし、検証・主要操作を確認する。
4. 信頼できる経路で公開し、必要なら使用中の配信基盤のキャッシュを更新する。
5. 公開コミット・日時を記録する。証拠を消すforce pushを通常の復旧方法にしない。

## 8. 再公開前確認

- 不審なファイル・通信・転送がなく、正常版の差分を確認した。
- 露出した認証情報は失効し、管理権限・連携を確認した。
- 全ページ、画像、記事、メニュー、キーボード、SNS、フォームを確認した。
- Formsの受付・所有者への受信・回答共有を確認した。
- 成果物に秘密、個人情報、バックアップ、内部ログがない。
- HTTPS、正規URL、検索設定、実際に設定したヘッダーを確認した。
- 実機・外部サービス等の未確認事項と残る課題を記録した。
- メンテナンス解除の判断者・日時・公開コミットを記録した。
