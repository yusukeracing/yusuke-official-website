# 公開・バックアップ・復旧手順

更新日：2026-10-30（日本時間）。GitHub Pagesは `dist/` の成果物を配信します。`docs/` は説明資料です。[公開範囲](PUBLICATION_BOUNDARY.md)、[CMS操作](CMS.md)、[改ざん対応](INCIDENT_RESPONSE.md) も参照してください。

## 1. 作業前とビルド

1. 最新 `main` を取り込み、未コミット変更を確認する。CMSとコード編集を並行する場合は互いのコミットを取り込む。
2. 写真原本と、公開してよい記事・設定が保存されているか確認する。許諾記録、フォーム回答、秘密は別管理する。
3. Pythonとビルド用の仮想環境を用意する。以下はLinux/macOSの例。Windowsでは仮想環境の `Scripts/python.exe` を使う。

```bash
python3 -m venv .build-venv
.build-venv/bin/python -m pip install -r requirements-build.txt
.build-venv/bin/python -c 'import PIL; print(PIL.__version__)'
.build-venv/bin/python scripts/build.py
.build-venv/bin/python scripts/check_site.py dist
```

Pillowは修正版13.0.0の固定依存を使います。既存のシステムPythonに旧版が残っていても、ビルドには上記の仮想環境を使います。失敗した場合は、依存環境、画像パス、大小文字、記事ID等のエラーを修正します。検証を飛ばした成果物を公開しません。

## 2. メンテナンス中に通常画面を確認する

今回作業開始時の最新CMS保存値は `maintenanceEnabled: true` です。確認のため本番設定をOFFへ変えず、別フォルダへ通常画面を生成します。

```bash
.build-venv/bin/python scripts/build.py --normal-preview --output dist-preview
.build-venv/bin/python scripts/check_site.py dist-preview
.build-venv/bin/python -m http.server 8000 --bind 127.0.0.1 --directory dist-preview
```

`dist-preview/` は手元確認用です。公開先 `dist/` と取り違えず、プレビューや納品ZIPをGitの追跡対象へ追加しません。

## 3. CMS保存から公開まで

1. Pages CMSで対象リポジトリと編集ブランチを確認する。本人が直接公開する運用では `main` を選ぶ。
2. 記事・写真を変更して保存する。CMSのエラーを保存成功と扱わない。
3. GitHubのコミット履歴で対象ファイル・変更内容が保存されているか確認する。
4. [GitHub Actions](https://github.com/yusukeracing/yusuke-official-website/actions)で、そのコミットの `Validate and deploy Pages` の成功を確認する。
5. 公開ページを再読み込みし、記事・写真・公開版の識別情報を確認する。

CMS保存が成功してもビルド・公開が完了するまでは前の公開版が続きます。コミットがない保存失敗と、コミット後の公開待ちを分けます。PR必須の場合は編集ブランチからレビュー後に `main` へ反映します。

Pages CMSは外部サービスのため、このサイトから管理画面の保存処理・権限・エラーUIを自由に変更できません。認証期限切れ、401/403、API制限、通信障害等では表示エラーを保存し、所有者が再認証・権限・利用状況を確認します。推測で現在の原因と断定しません。

## 4. 写真と記事

アップロード先は `assets/images/uploads/`、CMSの保存値も同フォルダからの相対パスです。先頭 `/` を付けません。元画像を保存し、ビルドで生成する `assets/optimized/` の配信画像を直接編集しません。アップロードしただけでは記事・トップの画像欄を選んだことにはなりません。

配信版には画像内容由来の識別子を使い、原本・配信版の寸法・ハッシュを画像manifestで区別します。原本は上書きしません。差し替えはアップロード、画像欄の選択、保存、GitHub差分、公開の順に確認します。

記事の公開対象外スイッチはWeb掲載を止めるものです。PublicリポジトリのJSON・履歴は読めるため、機密下書き・未承認個人情報を保存しません。公開済み記事IDを変えるとURLが変わるので通常は固定します。

## 5. 本番公開

1. 通常画面・必要なメンテナンス画面を確認し、実施結果と未確認環境を記録する。
2. 公開可能な変更をGitHubへ保存する。PagesのSourceはGitHub Actionsとする。
3. ビルド・検証・公開ジョブの成功を確認する。失敗時はエラーを保存し、前の公開版が続いているか確認する。
4. 本番URLで表示・画像・記事・メニュー・SNS・フォームを確認する。フォームは所有者がテスト回答の受信まで確認する。

公式Actionsは完全なコミットSHAで固定し、ビルドは読み取り、公開ジョブだけPages/ID tokenの書き込みを持ちます。Environment承認条件やGitHub保護ルールは所有者のアカウント設定です。

## 6. メンテナンスと再開

CMS「サイト設定・SNS」のメンテナンスをONにして保存・公開すると、既存ページと404を案内文へ切り替えます。サーバー停止や手動の404差し替えは不要で、JavaScript無効時にも表示します。

再開時はOFFで保存し、公開成功と通常画面を確認します。現在のメンテナンス解除は確認結果と運用判断に合わせて行います。ソースHTMLや写真原本を消す操作ではありません。

既存URLはHTTP 200、存在しないURLはHTTP 404です。この設定だけで503や `Retry-After` は返せません。メンテナンス中は `noindex` と記事URLを含めないサイトマップに切り替え、解除後に通常設定へ戻します。

メンテナンスは認証ではなく、既存タブ・外部キャッシュ・Publicリポジトリの履歴や原本を非公開にする機能でもありません。Pages自体の停止中は案内も配信できません。

## 7. ドメイン・重複URL・キャッシュ

Cloudflareで取得したドメインも使用できます。PagesのCustom domain、Cloudflare DNS、CMSの公開URLを正規URLへそろえ、canonical・OGP・サイトマップ・HTTPSを確認します。未提供のドメインやDNS値を推測して設定しません。

同一サイトを別ホスティングへ無計画に配置しません。移行時は正規URLを一つにし、転送と検索向けURLを確認します。canonicalは著作権上の重複・無断転載を検査する機能ではありません。

写真は内容由来URL、CSS/JSは参照バージョンで更新します。古い表示では、まず保存コミットと公開ジョブを確認し、成功後に再読み込みします。Cloudflareを実際に使う場合だけ、そのキャッシュ設定・パージを確認します。

## 8. ヘッダーとアカウント

HTMLのCSP/referrer metaを維持します。GitHub Pagesでは任意HTTPヘッダーをファイルだけで指定できません。Cloudflare等で追加した場合は、実レスポンスを確認してから有効化済みと記録します。[セキュリティ確認](SECURITY.md) を参照してください。

所有者はGitHub・CMS・Googleの編集者とAppを必要最小限にし、2段階認証・復旧手段・不要な連携削除を管理します。Forms/Sheetsの回答一覧を公開しません。

## 9. バックアップ

- 大きな更新・整理の前に、Git履歴を含むリポジトリを公開サイトと別の保管先へ保存する。
- 写真原本、掲載許諾、戦績根拠、ドメイン・CMS復旧手順を別保管する。許諾書や個人情報をPublicリポジトリへ追加しない。
- Forms/Sheets回答は所有者の権限下で必要な期間保存し、運用方針に従って整理する。
- 検証済み成果物に対応するコミットID・依存バージョン・公開日時を記録する。配信画像だけを原本の代わりにしない。

バックアップがあることと復元できることは別です。別フォルダからビルドし、記事・画像を復元できるか確認します。

## 10. 正常版へ復旧

1. 公開差分と正常コミットを特定し、現状の証跡を残す。
2. 正常版の別チェックアウトで依存を用意し、ビルド・検証・主要操作を確認する。
3. 不具合の変更を打ち消すコミットや復旧PRを作る。CMSで増えた正当な記事・写真を巻き戻さないよう差分を確認する。
4. `main` 反映・公開成功を確認し、必要なら実際の配信基盤のキャッシュを更新する。
5. 解除前に画像・記事・リンク・フォーム・HTTPS・正規URLを確認する。

改ざん・流出が疑われる場合は先に [対応テンプレート](INCIDENT_RESPONSE.md) で影響・認証情報・原因を確認します。古いファイルへ戻すだけで終えず、Gitのforce pushで証拠を消す方法を通常の復旧手順にしません。
