## 今回の修正と、原因と断定しない項目

- 指定された09を正しい相対パスで登録し、静的HTMLと公開用JSONの両方へビルド時に同期します。JS読み込み前・無効時にも旧HTMLの画像へ戻らないようにする改善です。
- CMSの写真管理ルートを`assets/images`へそろえます。以前の`assets/images/uploads`だけでは既存直下の写真と管理範囲が異なっていました。この範囲の差は設定から確認できますが、今回の画像選択失敗の直接原因だったかはCMS実画面未確認のため断定しません。
- サブディレクトリ公開に対応する相対パスを使い、生成した配信用画像と公開JSONの参照先も一致させます。
- 配信用画像の識別子・公開情報を使い、旧画像のキャッシュと新しい公開版を区別できるようにします。「キャッシュを消せば直る」と保存内容の不一致を片付けません。
- 調査開始時のメンテナンスONは保持します。通常サイトのプレビュー確認と、メンテナンス公開の確認を分けます。

## 保存から表示までの経路

```text
Pages CMSのフォーム
  ↓ 選択ブランチへ保存
GitHubのdata/*.json と assets/images/*
  ↓ mainへの更新で起動
GitHub Actionsのビルド・検証
  ↓ 成功した成果物だけを公開
GitHub Pagesへdist成果物を配信
  ↓ HTMLと公開JSON・配信用画像を取得
訪問者のブラウザ
```

CMSの編集先はソースの`data/`です。`dist/`は自動生成先で、CMSから直接編集しません。`docs/`は説明資料で、このワークフローのWeb公開ルートではありません。公開対象はActionsがアップロードする`dist/`です。公開GitHubリポジトリ上のソース・履歴が読めることは、このWeb配信範囲とは別です。

## 処理中・成功・失敗を確認できる範囲

このリポジトリでは、外部サービスであるPages CMS自体の保存ボタン・保存通知・GitHub App認証画面を変更できません。独自の管理ログインを追加して、その制約を隠す対応は行いません。

CMSの表示、GitHubへのコミット、Actionsの結果、公開版の内容は別の状態です。保存成功通知だけで公開成功と扱わず、Actionsの最新処理まで確認します。公開ページでコンテンツの取得に失敗した場合は、既に表示できる静的本文を残す構成にします。ブラウザが表示できたことだけでは、CMS保存の成否を証明しません。

## 所有者が最後に行う短い確認

1. CMSでテスト記事を作り、サムネイルと本文写真2枚、それぞれの代替テキスト・説明を登録します。
2. 保存後のコミットとActions成功を確認し、通常表示で一覧・詳細へ移動します。メンテナンスONのまま公開する場合は、別の通常プレビューで確認します。
3. 文章と写真を変更して再保存し、変更の反映を確認します。
4. 掲載OFF→再掲載を試し、最後にテスト記事を削除して、一覧・詳細ファイル・サイトマップから外れたことを確認します。
5. Googleフォームへ、テストと分かる内容を1件送信し、所有者が回答一覧で受信を確認します。確認後、不要なテスト回答を整理します。

本番へテスト記事を残す必要はありません。秘密情報や実在の個人の非公開情報を試験データへ使わず、画像も掲載権限のあるものを選びます。
