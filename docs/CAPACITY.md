# 同時接続・配信能力の確認

このサイトは GitHub Pages が配信する静的サイトです。「何人まで同時に閲覧できるか」という本番の上限人数は、このクラウド環境での測定だけでは決定できません。Google Forms 側の受付能力も別のサービスの条件に従います。

## 実測結果（2026-10-29 13:30 日本時間）

今回の最大試験は **100並列クライアント** で、200回のページ読み込み・3,000件のHTTP取得がすべて成功し、転送内容の検証も一致しました。読み込み全体のp95は **1.86秒**、この段階全体の実行時間は2.20秒でした。**これは今回試した最大値であって、サイトの限界値でも、本番で100人を保証した結果でもありません。**

| 設定した並列クライアント数 | 観測した同時HTTP要求の最大 | 完了したページ読み込み / 計画 | HTTP取得件数 | ページ全体p95（ms） | 失敗 / 時間切れ中止 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 2/2 | 30 | 11.54 | 0 / 0 |
| 10 | 10 | 20/20 | 300 | 120.03 | 0 / 0 |
| 25 | 25 | 50/50 | 750 | 342.74 | 0 / 0 |
| 50 | 50 | 100/100 | 1,500 | 833.85 | 0 / 0 |
| 100 | 100 | 200/200 | 3,000 | 1859.77 | 0 / 0 |

100クライアントの段階で、サーバーが同時に受理済みだったTCP接続は最大82本でした。要求中のクライアントは最大100であり、接続待ちや処理待ちも含みます。100本の接続が常時成立していたという意味ではありません。

1ページ読み込みは15ファイル・458,716バイト（約448KiB）の本体転送です。全段階合計で5,580件を取得しました。実行環境はPython3.12.14 / Linux、CPUクォータは4CPU相当（`cpu.max=400000 100000`）、メモリー上限32GiB、測定プロセスの最大RSSは47.95MiBでした。クライアントとサーバーはこの同じ環境内で動いています。

実行時刻、対象ファイルとSHA-256、転送量、各段階のp50・p95・最大値、観測した接続数は [測定結果JSON](load-results.json) に保存しています。ファイルを変更したあとに再実行した場合、値も変わります。

## 今回行う測定の範囲

`scripts/load_check.py` は、ビルド済みの `dist/` に対し、同じマシン内の `127.0.0.1` だけで HTTP 通信を発生させます。公開サイト、GitHub Pages、Google Forms、SNS、Analytics に負荷をかけません。外部の URL を指定するオプションもありません。

1つのクライアントは、TOPのHTML、CSS、JavaScript、HERO画像、アイコン、初期JSONを順番に取得します。各レスポンスの HTTP 200、Content-Length、受信バイト数、SHA-256 を検証します。ページ途中で読み込むギャラリー全画像や外部iframeは、この初期表示の測定に含めません。

同時クライアント数を 1 / 10 / 25 / 50 / 100 と増やし、各クライアントが同じ読み込みを2回実行します。クライアント側のキャッシュは使わず、毎回ファイル本体を転送します。OSのファイルキャッシュは消去しません。計測にはクライアントを作成する時間も含めます。

安全のため、最大100クライアント、合計10,000リクエスト・512MiBの予定転送量、各段階30秒の終了判定、各通信最大3秒の待ち時間を設けています。サーバーと接続は測定終了時に停止・解放します。HTTPサーバーはローカル測定専用の Python ThreadingHTTPServer、HTTP/1.1、待ち行列128、TCP_NODELAY有効です。これらは GitHub Pages の設定や契約値ではありません。

**同時クライアント数・同時HTTP接続数・同時閲覧人数は同じ値ではありません。** ブラウザー1人が複数の接続を使う場合があり、閲覧中でも通信していない人がいます。また、今回のクライアントとサーバーはCPU・メモリーを共有しています。DNS、TLS、実際の通信回線、CDNキャッシュ、地域差、Google Forms の処理は測っていません。

## 再実行

Python 3の標準ライブラリだけで実行できます。ビルド中やファイル編集中に測定すると整合性検証が失敗するため、生成物を確定してから実行します。

```bash
python3 scripts/build.py
python3 scripts/check_site.py dist
python3 scripts/load_check.py --directory dist --max-concurrency 100 --journeys-per-client 2 --output docs/load-results.json
```

最大100クライアントまでの測定でエラーがなくても、それをサービスの上限や人数保証として扱いません。測定結果は、実行した負荷・端末・サーバーにおける観測値です。レスポンス時間のp50は中央値、p95は95パーセンタイル、TTFBはレスポンスヘッダー受信までの時間です。転送バイト数はレスポンス本体のみで、HTTPヘッダー等は含みません。

## 本番環境の見積もり方

GitHub Pages の公式ドキュメントには、2026-10-29確認時点で月100GBの**ソフト**帯域制限、必要に応じたレート制限（HTTP 429）等が記載されています。固定の「同時閲覧者○人まで」という保証値は示されていません。最新条件を確認してください。

- [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)
- [確認に使った公式ドキュメントのソース](https://github.com/github/docs/blob/main/content/pages/getting-started-with-github-pages/github-pages-limits.md)

本番で必要な人数・地域・利用時間が決まった場合は、CDN等の利用プラン・帯域条件と、1訪問当たりの実際の通信量を確認します。自分で管理する検証環境と計測範囲を決め、外部サービス側の利用条件を満たす範囲で試験します。今回の測定は、公開サイトへの大量通信や、DDoS耐性の実証ではありません。
